On 4 June 1996, Ariane 5 lifted off from Kourou on its first flight. It carried two inertial reference computers, the
SRIs, that tell the rocket which way it is pointing. They were identical on purpose: if one failed, the other would
take over.

At 36.7 seconds after main engine ignition, the backup failed. A twentieth of a second later, the active one failed
too, for exactly the same reason. At 39 seconds the rocket was breaking apart.

This episode rebuilds that chain as code. Everything below runs the same simulation that the
[episode’s tests](https://github.com/sriramamuthan/postmortem-lab/tree/main/incidents/01-ariane-5) check.

## Fly it

## What happened, in order

Every step here comes from the inquiry board’s report.

1. **The code was borrowed.** The SRI and its software were practically the same as on Ariane 4, which had flown
   successfully for years.
2. **One function should not have been running at all.** The alignment function only works before lift-off. On
   Ariane 4 it kept running for about 40 seconds of flight, so a countdown on hold could restart quickly. Ariane 5
   didn’t need that, but the code was kept for commonality.
3. **It converted a number without checking it.** The function turned the *horizontal bias*, BH, from a 64-bit float
   into a 16-bit signed integer, which holds at most 32,767. Seven conversions like this had been flagged as risky.
   Four were protected. Three, including BH, were left unprotected to keep the computer under an 80% workload target,
   on reasoning that “turned out to be faulty”.
4. **Ariane 5 was faster.** Its horizontal velocity builds up five times faster than Ariane 4’s, so BH went past
   32,767. The Ada code raised an *Operand Error*.
5. **Both computers stopped.** The specification said any exception meant: report it, save the details, shut the
   processor down. That makes sense for a random hardware fault, because the backup takes over. But both SRIs ran the
   same software on the same data. The backup had already stopped one 72 ms cycle earlier.
6. **The flight computer flew on garbage.** It read SRI 2’s diagnostic bit pattern as attitude data, saw a huge
   deviation that wasn’t there, and swung the booster nozzles, then the main engine nozzle, to full deflection. The
   angle of attack passed 20 degrees and the rocket broke up.

<Callout type="lesson">
A backup that runs the same code on the same inputs protects you from hardware faults, not from your own bugs. Both
copies fail together.
</Callout>

## Fix it three ways

Tick each fix in the demo and launch again. Any one of them is enough.

| Fix | Where it comes from | What changes |
|---|---|---|
| Protect the BH conversion | The other four variables already were | BH saturates at 32,767 instead of raising an error |
| Switch alignment off at lift-off | Board recommendation R1 | The function never runs in flight, so BH is never computed |
| Keep sending best-effort data | Board recommendation R3 | The error is handled and the SRI keeps flying |

The board’s other key recommendation, R2, was to test the real equipment with the real trajectory. That is what the
episode’s test file does: it flies Ariane 5’s trajectory through the SRI code and expects the failure, then checks
each fix. Had a test like that run in 1996, the report says “the failure mechanism would have been exposed”.

## What I simplified

The real BH values are in the board’s restricted technical report, so this simulation models BH from the time since
lift-off. It’s calibrated to cross 32,767 at H0 + 36.7 s, and Ariane 4 builds up five times more slowly, as the report
says. Lift-off at H0 + 7 s and the attitude response are tuned to reproduce the report’s timings. The order of events,
the 72 ms cycle, the shared fault and the fixes are as documented.
